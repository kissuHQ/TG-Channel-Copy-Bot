TITLE: Write a Markdown/HTML formatting reference to be embedded in the Help system

CONTEXT
Users setting caption_parse_mode to "md" or "html" (via /caption command
or the dashboard's Caption format dropdown, pair-caption-mode) often
don't know the actual syntax — e.g. how to bold text, add a clickable
link, italicize, etc. This step produces the reference CONTENT; Step 5
wires it into the actual Help command/page.

REQUIRED CONTENT
Write a compact formatting reference covering, for BOTH Markdown and
HTML (Telethon's two supported parse_mode values used by this bot):
- Bold, italic, underline, strikethrough
- Inline code and code blocks
- Clickable links (both "hyperlink text" style and raw URLs)
- Line breaks / paragraph spacing behavior (note any quirks specific to
  Telegram's Markdown flavor vs standard Markdown, e.g. Telegram does NOT
  support headers, bullet lists, or nested formatting the way GitHub-
  flavored Markdown does — only state what Telegram actually renders,
  verify against Telegram's own formatting documentation rather than
  assuming standard Markdown/HTML behavior applies).
- At least 2-3 short worked examples per mode showing raw input next to
  what it looks like when rendered in Telegram (e.g. "*bold text*" (or
  "**bold text**" for MarkdownV2, be precise about which Telegram accepts) 
  renders as **bold text**).
- A short note on the caption_template placeholders from Step 2 combined
  with formatting, e.g. how to bold the {filename} placeholder output.
- A short "Plain text" explanation of when to use caption_parse_mode=plain
  (no formatting applied at all, safest option if the source captions
  already contain characters that could break Markdown/HTML parsing,
  like unescaped * or < characters).

FORMAT
Deliver this as structured content (e.g. a Python dict/list of
{title, body} sections, or a small JSON/markdown block) that Step 5 can
directly render both inside a Telegram bot message (HTML-formatted, split
across reasonable message lengths) and inside the dashboard Help page
(as HTML/markdown). Do not hardcode it as one giant inline string glued
into bot_help() — structure it so Step 5 can pull individual sections out
per category/button.

ACCEPTANCE CRITERIA
- Content is technically accurate for what Telegram/Telethon actually
  renders (verify against Telegram's official formatting docs, not
  general Markdown/HTML knowledge, since Telegram's flavor is
  non-standard in several ways).
- Reads clearly for a non-technical user, in the same casual Hinglish
  style already used elsewhere in this bot's user-facing text.

TITLE: Replace flat /help and .help with a categorized, button-driven help
system, and add a matching Help page to the dashboard

BUG LOCATION
- main.py — cmd_help() (.help, around line 970-992)
- main.py — bot_help() (/help, around line 1441-1467)
- main.py — CommandHandler("help", bot_help) registration (~line 3855)
- templates/base.html — nav sidebar (around line 18-25)
- New: templates/help.html
- static/multipage.js, static/multipage.css

WHAT IS HAPPENING
Both .help and /help currently dump every command as one long flat
message. This is hard to read, doesn't explain WHEN/WHY to use a feature
(only lists command syntax), and there is no help page anywhere in the
dashboard (only Overview, Tasks, Channel pairs, Global settings exist in
the nav). This step fixes both.

CONTENT SCOPE — confirm every real command/feature is covered, sourced
from the actual registered handlers, not guessed:
  Bot commands currently registered (verify this list is still accurate
  against app.add_handler calls before writing help text — it may have
  changed since this audit): /start, /help, /setsource, /settarget,
  /info, /status, /pause, /resume, /stop, /reset, /sync, /force_sync,
  /syncfrom, /synclast, /refresh, /tasks, /autoforward, /caption,
  /setthumbnail, plus the Continue inline button callback.
  Userbot (.) commands: .setsource, .settarget, .info, .status, .pause,
  .resume, .stop, .reset, .sync, .syncfrom, .synclast, .refresh, .help.
  Dashboard features (these have no bot command equivalent — document
  them as dashboard-only): creating/editing/deleting pairs, per-pair
  include/exclude keywords, allowed message types, rate profile, daily
  message/media limits, schedule window, quiet hours, max posts/hour,
  caption template + type toggles + parse mode, thumbnail upload, dry-run
  preview, task priority, bulk task actions, notification settings,
  storage cleanup.

REQUIRED CATEGORIES (bot side)
Group into logical categories — suggested grouping, adjust if a command
fits better elsewhere, but keep every real command/feature placed in
exactly one category so nothing is mixed up or duplicated:
  1. "🚀 Setup" — setsource, settarget, info (getting a pair or the
     legacy default source/target configured)
  2. "🔄 Sync & Tasks" — sync, force_sync, syncfrom, synclast, tasks,
     pause, resume, stop, refresh (running and managing bulk transfers)
  3. "⚡ Auto-forward" — autoforward, and an explanation of what it does
     differently from a manual sync (live vs bulk), plus a pointer to the
     dashboard's per-pair auto_forward toggle
  4. "✏️ Caption & Thumbnail" — caption command + template placeholders +
     the formatting guide content from Step 4, setthumbnail
  5. "⚙️ Limits, Schedule & Status" — status, reset, plus explanations of
     daily message/media limits, hourly caps, and schedule/quiet windows
     (dashboard-only settings — explain what they do and where to set
     them even though there's no bot command for them)
  6. "🌐 Dashboard-only features" — a short category explaining pairs
     management, dry-run, bulk actions, and notification settings live
     only on the web dashboard, with a reminder of the dashboard URL/path

IMPLEMENTATION — bot side (/help and .help)
1. Replace bot_help() with an initial message showing only the category
   list as inline buttons (InlineKeyboardMarkup, one button per category
   from the list above), plus 2-3 lines of the most essential basics
   (e.g. how to set a source/target and start a sync) so a brand-new user
   isn't stuck looking at only buttons with zero content.
2. Add a CallbackQueryHandler (pattern like r"^help:") that, when a
   category button is tapped, edits the message to show that category's
   commands AND a short explanation of when/why to use each one (not just
   command syntax — e.g. for autoforward: "naye posts turant automatically
   copy karne ke liye — agar tumhe purane messages bhi chahiye to pehle
   ek /sync bhi chalao"). Include a "⬅️ Back to categories" button on
   every category view.
3. For .help (Telethon userbot side), since it can't use inline buttons
   the same way as easily... actually Telethon DOES support inline
   buttons via event.edit(..., buttons=...) — implement the same
   category/back-button pattern here too, matching the bot's UX as
   closely as Telethon's button API allows. If Telethon buttons prove
   impractical for outgoing-message-triggered commands in this account's
   context, fall back to a single well-organized message with clear
   category headers (### style dividers) instead of one undifferentiated
   list — but attempt the button version first.
4. Make sure every category's content fits Telegram's message length
   limits (a single category should never need splitting, given they're
   only a handful of commands each).

IMPLEMENTATION — dashboard side
1. Add templates/help.html following the same structure/style as the
   other page templates (base.html extension pattern already used by
   dashboard.html/tasks.html/pairs.html/settings.html).
2. Add a Flask route (e.g. @flask_app.route("/help")) rendering it,
   protected by the same login-required check already added to the other
   page routes.
3. Add a nav link in templates/base.html's sidebar (around line 18-25),
   in the same style as the existing Overview/Tasks/Channel
   pairs/Global settings links.
4. Structure the page with collapsible/tabbed sections matching the same
   6 categories used on the bot side, so a user switching between bot and
   dashboard sees a consistent mental model. Include the full Markdown/
   HTML formatting guide from Step 4 in the Caption & Thumbnail section.
5. Cover dashboard-only features here in full detail (these don't need a
   bot-side entry beyond the pointer in category 6), since this is the
   one place a user can see every field/toggle/setting explained.

- /help and .help both show a category menu first, not a wall of text.
- Tapping any category shows that category's commands with a short
  "when/why to use this" explanation for each, not just syntax.
- Every command currently registered in app.add_handler is present in
  exactly one category — do a final pass cross-checking the handler list

- Every dashboard-only feature (pairs, dry-run, bulk actions, schedule/
  quiet hours, notification settings, storage cleanup) is documented
  somewhere in the help content, either bot-side or dashboard-side.
- New /help (dashboard) page is reachable from the sidebar nav, requires
  login like every other page, and matches the visual style of the
  existing pages (don't introduce a different design language).
- The Markdown/HTML formatting guide is visible and readable inside the
  Caption & Thumbnail help category on both bot and dashboard.

DO NOT
- Do not change the actual behavior of any command — this step only adds
  a discovery/help layer around the existing commands and features.
- Do not remove /start or its existing behavior — only bot_help() is
  being restructured.
